# Propview Guide: API Keys, Usage, and the Codebase

One consolidated guide for three different questions people ask about
this repo: *where do I put my API keys*, *how do I actually use the
product*, and *how is this codebase put together*. Each of those is its
own section below — jump to the one you need. This guide points at the
authoritative doc for anything it doesn't fully explain itself; it
doesn't duplicate what's already documented well elsewhere.

- **First time here?** Read "1. Setup" then "2. API Keys" enough to run
  the Quickstart.
- **Onboarding a real tenant / running the product?** Section 3.
- **Contributing code / extending it?** Section 4.
- **Deploying for real?** Section 5.

---

## 1. Setup

```bash
git clone <this repo>
cd Propview
./scripts/setup_dev_env.sh
source .venv/bin/activate
```

This creates one shared Python venv, installs every service's
`requirements.txt`, downloads the spaCy model PII masking needs, and
generates real `.env` files (from each `.env.example`) with the
cross-service shared secrets (`ENCRYPTION_KEY`, `INTERNAL_SERVICE_TOKEN`)
correctly propagated to every file that needs the *same* value — see
`../scripts/README.md` for exactly what it does and what it verified.
Safe to re-run; it never overwrites a `.env` that already exists.

You still need, at minimum, a **`GEMINI_API_KEY`** (free, see section 2)
for anything to actually talk to the AI model. Put it in
`services/gemini-client/.env` *before* running the setup script and it
propagates automatically to every other `.env` that needs it too.

**Prove it works, no phone/mic/extra accounts needed:**

```bash
cd services/orchestrator
python tests/test_orchestrator_live.py
```

This needs a local Postgres, Redis, and `livekit-server --dev` running
(see `../infra/livekit/LOCAL_TESTING.md`) — it proves the core
audio-to-Gemini loop end to end with a real LiveKit server and a fake
Gemini session (no API cost). For the real thing with a real Gemini
call, see section 3's "Running a call."

## 2. API Keys & Credentials — Where Everything Goes

Two different kinds of credential in this system, handled two completely
different ways:

- **Process-level secrets** (Gemini, Twilio, Deepgram, LiveKit, internal
  auth tokens): plain environment variables, one `.env` file per service,
  read at process startup. This is what most of this section covers.
- **Per-tenant credentials** (a specific agency's Google Calendar OAuth
  tokens): **not** an env var at all — submitted via the Admin API,
  encrypted at rest, one row per tenant. See section 2.4.

### 2.1 The one key you actually need to get started

| Key | Where to get it | Goes in |
|---|---|---|
| `GEMINI_API_KEY` | Free, no billing required for the rate limits this needs: https://aistudio.google.com/apikey | `services/gemini-client/.env` (propagates to `orchestrator`, `tool-router`, `db/ingestion` automatically via `setup_dev_env.sh`) |

Nothing else is required to run the core voice loop against a fake phone
line (`test_orchestrator_live.py`) or exercise the tool-calling path with
real text (`services/tool-router/README.md`'s live-verification steps).

### 2.3 Secrets that must match across files — don't regenerate them independently

Two values are **shared secrets**, not independent per-service config —
generating a different random value in each file breaks the services
that need to agree on it:

- **`ENCRYPTION_KEY`**: `admin-api` (encrypts calendar credentials) and
  `tool-router` (decrypts them to actually use them). Two different keys
  = tool-router can never decrypt what admin-api wrote.
- **`INTERNAL_SERVICE_TOKEN`**: `orchestrator` (sends it on every Tool
  Router call) and `tool-router` (checks it). Two different values = every
  call gets rejected with 401.

`./scripts/setup_dev_env.sh` handles this correctly for you automatically
(reads an existing value if one `.env` already has it, generates once
and reuses everywhere it's needed otherwise). If you're setting these up
by hand instead, copy the *same* generated value into both files.

`PLATFORM_OPERATOR_TOKEN`, by contrast, is **not** shared with anything —
it lives only in `admin-api/.env`.

### 2.4 Per-tenant credentials (Google Calendar) — not a `.env` var

A specific agency's Google Calendar OAuth tokens are **not** a process
env var — they're submitted once per tenant via the Admin API and stored
Fernet-encrypted in Postgres (`tenant_settings.encrypted_calendar_credentials`).
See `services/scheduling/README.md`'s "Credentials" section for how to
actually obtain a Google Calendar OAuth refresh token, and section 3.2
below for the exact `curl` call. This is deliberate: one orchestrator
deployment serves many tenants, and each tenant's calendar belongs to a
different Google account.

## 3. Using the Product

### 3.1 Onboard a new tenant (agency)

Full walkthrough with all the exact `curl` commands:
**`docs/AGENCY_ONBOARDING.md`**. Short version:

```bash
# 1. Provision the tenant -- get its admin API key (shown once, save it)
curl -X POST localhost:8001/admin/tenants/austin-realty/provision \
  -H "Authorization: Bearer $PLATFORM_OPERATOR_TOKEN"
# -> {"tenant_id": "austin-realty", "admin_api_key": "..."}

# 2. Upload listings
curl -X POST localhost:8001/admin/tenants/austin-realty/listings \
  -H "Authorization: Bearer $ADMIN_API_KEY" -H 'Content-Type: application/json' \
  -d '{"listings": [{"address": "123 Oak St", "city": "Austin", "state": "TX",
       "property_type": "house", "beds": 3, "baths": 2.0, "price": 520000}]}'

# 3. Set agency branding (spoken by the agent)
curl -X PUT localhost:8001/admin/tenants/austin-realty/branding \
  -H "Authorization: Bearer $ADMIN_API_KEY" -H 'Content-Type: application/json' \
  -d '{"agency_name": "Austin Realty"}'

# 4. Set calendar credentials (needed for site-visit booking)
curl -X PUT localhost:8001/admin/tenants/austin-realty/calendar-credentials \
  -H "Authorization: Bearer $ADMIN_API_KEY" -H 'Content-Type: application/json' \
  -d '{"provider": "google", "credentials": {"refresh_token": "...", "client_id": "...", "client_secret": "..."}}'
```

For unstructured docs (brochures, FAQs) the agent should be able to
answer from, use `db/ingestion/` instead — see its own README.

### 3.2 Run a call

```bash
# Shared infra, once:
cd db/migrations && python apply_migrations.py
cd ../../services/tool-router && uvicorn main:app --port 8000 &
cd ../admin-api && uvicorn main:app --port 8001 &

# One call, for one tenant:
cd services/orchestrator
TENANT_ID=austin-realty python main.py <room-name>
```

`main.py` is deliberately a "one process, one call" entrypoint today —
it joins the named LiveKit room and bridges it to Gemini for that call's
lifetime. It does not yet auto-dispatch onto every new inbound SIP call;
that needs LiveKit's Agent Worker / job-dispatch system, wired in once a
real telephony deployment (section 5) exists to dispatch against.
`AGENCY_NAME`/branding is looked up per-tenant automatically (section
2.4) — you don't need to pass it on the command line.

`<room-name>` needs a real caller publishing audio into it. For local
testing without a phone, see `services/orchestrator/tests/test_orchestrator_live.py`
and the other `tests/test_*_live.py` scripts, each of which simulates a
caller by publishing recorded audio to a real LiveKit room.

### 3.3 Admin API cheat sheet

Full reference: `services/admin-api/README.md`. Every route below
(except `/health`) needs `Authorization: Bearer <tenant's admin_api_key>`
from step 1 above.

| Action | Route |
|---|---|
| Provision a tenant (needs `PLATFORM_OPERATOR_TOKEN`, not a tenant key) | `POST /admin/tenants/{id}/provision` |
| Upload listings | `POST /admin/tenants/{id}/listings` |
| Set/get branding | `PUT` / `GET /admin/tenants/{id}/branding` |
| Set/get calendar credentials | `PUT` / `GET /admin/tenants/{id}/calendar-credentials` |

### 3.4 Talking to the agent directly (no phone) for a quick manual check

`tests/e2e-voice/harness.py`'s `send_text()` approach is the pattern
every live-verification script in this repo uses to exercise a real
Gemini conversation without a microphone — see
`services/orchestrator/tests/test_lead_qualification_live.py` for a
short, readable example: connect a `GeminiLiveSession`, call
`send_text("...")`, and read back the tool calls and spoken response
events.

## 4. The Codebase (for developers)

### 4.1 Mental model

A phone call is a WebRTC/SIP session in **LiveKit**. One Python process
(`services/orchestrator/main.py`) joins that room as a second
participant, streams the caller's audio to **Gemini Live** (native
speech-to-speech, no separate STT/TTS in the normal path), and streams
Gemini's audio back into the room. When Gemini decides to call a tool
(`search_properties`, `book_site_visit`, ...), the orchestrator forwards
that call over HTTP to the **Tool Router**, which runs the real
Postgres/Redis-backed logic and returns a result Gemini incorporates
into its spoken reply. Everything is **multi-tenant** via Postgres
Row-Level Security, keyed by a plain `tenant_id` string threaded through
every call.

```
Caller (PSTN/SIP)
   │
   ▼
LiveKit (WebRTC media server + SIP gateway)
   │  audio in/out
   ▼
Orchestrator (services/orchestrator) ──HTTP+auth──▶ Tool Router (services/tool-router) ──▶ Postgres (RLS) / Redis
   │  WebSocket                                         ▲
   ▼                                                     │
Gemini Live API                              Admin API (services/admin-api) ◀── agency ops (listings, branding, calendar creds)
   │  (on degradation)
   ▼
Cascaded fallback (services/fallback-pipeline): Deepgram → GPT-4o-mini → Cartesia
```

### 4.2 Repository layout

```
scripts/         Dev environment setup (venv + .env wiring) -- start here
infra/           Provisioning & deployment: telephony (Twilio), LiveKit, GCP, observability (Grafana/Prometheus)
services/
  gemini-client/   Gemini Live API WebSocket client (audio + tool-call + transcript events)
  audio-pipeline/  Raw G.711<->PCM resampler (built, not on the LiveKit hot path -- see its README for why)
  vap-sidecar/     Silero VAD -- predictive barge-in, runs in-process in the orchestrator
  orchestrator/    The call-handling process: main.py + the event loop wiring everything together
  tool-router/     FastAPI service executing Gemini's tool calls against real Postgres/Redis
  admin-api/       FastAPI service for tenant onboarding (listings, branding, calendar creds)
  lead-engine/     BANT scoring rules (used by tool-router's update_lead_qualification)
  scheduling/      Google Calendar client, Redis slot locking, Twilio SMS dispatch
  fallback-pipeline/  Deepgram+GPT-4o-mini+Cartesia cascade + health monitor, swaps in when Gemini degrades
  compliance/      Fair Housing filter, PII masking, escalation docs
  prompts/         System prompt / persona template
db/
  migrations/      Postgres schema, applied in order by apply_migrations.py
  ingestion/       Brochure/FAQ -> pgvector embedding ingestion script
tests/
  e2e-voice/       Text-driven multi-turn scenario battery (PROP-604/207)
  integration/     Real latency benchmarking
  load/            Locust load test against a real LiveKit server
docs/            You are here. Also: architecture.md, AGENCY_ONBOARDING.md, sprint-notes/
```

Each service directory has its own README mapping its contents back to
specific Sprint Plan ticket IDs (`PROP-1xx`..`PROP-6xx`) — those are the
authoritative source for what's built, what's tested, and what's a known
gap for that piece. This guide is the index and orientation layer, not a
replacement for them.

### 4.3 Auth model (read this before adding a new internal caller)

- **Orchestrator → Tool Router**: one shared secret
  (`INTERNAL_SERVICE_TOKEN`), since there's exactly one legitimate
  caller. See `services/tool-router/auth.py`.
- **Anyone → Admin API**: per-tenant API keys, not a shared secret —
  admin-api is tenant-facing (one real caller per tenant), so a shared
  secret would let any tenant act as any other. See
  `services/admin-api/auth.py`. A separate `PLATFORM_OPERATOR_TOKEN`
  gates only the provisioning route that mints those tenant keys.
- Both fail closed (500) if their configured secret is unset — never
  silently open.
- Both are also rate limited **per tenant**, via a Redis fixed-window
  counter (`rate_limit.py` in each service) — 120 req/10s on tool-router's
  `/tools/call`, 30 req/60s on admin-api's routes generally and a
  separate, tighter 5 req/60s just for `/provision`. This defends against
  one *authenticated* tenant monopolizing shared Postgres/Redis, not
  against unauthenticated traffic (auth above already rejects that first).

Full design rationale: `infra/observability/SECURITY_AUDIT.md` sections 3–4.

### 4.4 Multi-tenancy (read this before adding a new table)

Every tenant-scoped table has a plain `tenant_id TEXT` column and a
Postgres RLS policy (`db/migrations/004_row_level_security.sql`,
`FORCE ROW LEVEL SECURITY`) that's fail-closed: a connection that never
calls `SELECT set_config('app.tenant_id', $1, true)` sees **zero rows**,
not all rows. Every DB-touching service uses a `tenant_connection()`
context manager (`db.py` in tool-router/admin-api) that sets this
automatically — always go through it rather than a raw connection.
`DATABASE_URL` must point at the `propview_app` role
(`db/migrations/000_create_app_role.sql`), never a superuser — Postgres
always bypasses RLS for superusers.

### 4.5 Testing

Every service's own README documents its exact test command and current
pass count/date — that's the source of truth, not this list. Pattern to
know before you add a test:

- **Unit/integration tests** (`tests/test_*.py`, plain `pytest`): run
  against a real local Postgres/Redis, never mocked, because the actual
  point of most of them is proving RLS/encryption/locking behavior a
  mock would hide. `os.environ.setdefault(...)` near the top of each file
  sets safe local defaults.
- **Live tests** (`tests/test_*_live.py`, run directly with `python`, not
  `pytest`): need a real running dependency (LiveKit dev server, a real
  Gemini API key) and are the actual end-to-end proof a feature works,
  not just that its logic is correct in isolation. Each one's docstring
  says exactly what to start first.
- Third-party integrations with no real account available in this repo's
  dev environment (Deepgram/OpenAI/Cartesia/Google Calendar OAuth) are
  verified as far as possible without one: a request built for real and
  sent with a fake key, confirming it reaches that provider's own auth
  layer (a real 401) rather than failing locally first.

### 4.6 Extending the product — common changes and where they go

- **New Gemini tool**: define its Pydantic args model + handler in
  `services/tool-router/tools/`, register it in `main.py`'s `TOOLS` dict.
  It's picked up automatically as a Gemini `FunctionDeclaration` via
  `/tools/schema` — no orchestrator changes needed.
- **New fallback provider**: `services/fallback-pipeline/` implements the
  same `GeminiSessionLike` protocol (`send_audio`, `receive_events`, ...)
  `GeminiLiveSession` does — anything implementing that protocol is a
  drop-in swap via `orchestrator.py`'s `_switch_to_fallback()`.
- **New compliance rule**: `services/compliance/` — see
  `COMPLIANCE_AND_ESCALATION.md` for the filter's current scope and its
  own documented open design question (not yet live-wired into the call
  path).
- **New admin-api endpoint**: add the route with
  `dependencies=[Depends(require_tenant_auth)]` (or
  `require_platform_token` for a platform-level action) — see section 4.3.

## 5. Deployment Checklist (going from "built" to "live")

Everything in this repo is built and tested as far as this development
environment allows. Going live with a real phone number needs real
infrastructure this environment doesn't have:

1. **Twilio SIP trunk** (`infra/telephony/provisioning/`) — a real
   Twilio account + billing. `python provision_sip_trunk.py`.
2. **LiveKit media server + SIP gateway on a cloud VM**
   (`infra/gcp/provision_vm.sh` + `infra/livekit/`) — a real GCP project.
3. **TLS for the LiveKit signaling WebSocket** (`infra/livekit/Caddyfile`)
   — a real domain with DNS pointed at the VM's static IP from step 2.
   Optional: everything still works over plain `ws://` without it.
4. **Real third-party keys** for whichever optional integrations you
   want live: Deepgram/OpenAI/Cartesia (fallback), Google Calendar OAuth
   (per tenant, section 2.4), Twilio SMS (confirmation texts).
5. **Auto-dispatch on inbound calls** — `main.py` currently takes an
   explicit room name; production needs LiveKit's Agent Worker/
   job-dispatch system wired in so a new inbound call automatically
   spawns an orchestrator process, once step 2 exists to dispatch
   against.
6. **A pilot agency partner** — the plan's own rollout stages 3–8
   (dry-run testing, soft launch, monitoring, scaling) are an
   operational process with a real client, not something this codebase
   automates. See `Sprint Plan.md` section 9 and
   `docs/AGENCY_ONBOARDING.md`'s Stage 1–2 for what's already built
   toward it.

Every one of these has complete, ready-to-run code/scripts already in
this repo — what's missing is credentials and infrastructure this
development environment can't provide, not unwritten code.
